Payment Recovery

Operator-controlled recovery for expired, cancelled or interrupted final-balance handoffs. Existing Stripe sessions are reused when still open; a replacement is created only after the provider confirms the prior session is expired.

Duplicate-charge protection
  • No automatic charge, checkout creation, customer notification or recurring billing.
  • An already-open Stripe Checkout Session is reused instead of duplicated.
  • A paid or complete provider session blocks replacement and requires reconciliation.
  • An unknown provider state fails closed instead of guessing.
  • Expired/cancelled requests require an explicit operator recovery confirmation and a new future link expiry.

Operating Help

Why reuse an existing checkout?

Creating another provider session while the first remains open can leave two valid payment paths. Build 320 asks Stripe about the exact persisted session before replacement. Open sessions are reused.

When can a Stripe checkout be replaced?

Only when the operator has deliberately requested recovery and Stripe reports the previous Checkout Session itself as expired. Paid, complete or uncertain provider states do not create a replacement.

What if Stripe reports paid or complete?

Do not create another checkout. Open Payment Reconciliation to compare the provider session with the tracked payment request and booking final-payment ledger.

What happens after a customer returns from checkout?

The customer status page treats a return as unconfirmed until Rosie Dazzlers data records payment. While confirmation is unresolved, the page suppresses another checkout action so the customer is not encouraged to pay twice.

Does recovery notify the customer?

No. This cockpit always sends notify_customer: false. Sending or copying the customer link remains a separate deliberate operator action.
