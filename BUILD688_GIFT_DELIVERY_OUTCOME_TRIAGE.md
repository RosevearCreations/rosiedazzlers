# Build 688 — Gift Delivery Provider Outcome Exception Triage, Manual Recipient Confirmation & No-Resend Escalation

## Purpose

After Build 687 permanently reserves and reconciles the one-time gift-email dispatch, a signed-in **owner/admin** can independently record evidence about the provider outcome, verify an **actual recipient acknowledgment**, or escalate uncertainty without changing delivery or payment. Provider acceptance alone is **not** recipient confirmation. The original send slot remains consumed forever.

## Exact audited workflow

1. Open `admin-gift-recovery-review.html`, enter the exact checkout session, and refresh Build 688.
2. Select the original certificate and its immutable Build 687 dispatch attempt. Inspect provider outcome (`in_flight`, `provider_accepted`, `provider_rejected`, `outcome_unknown`) and the original provider receipt.
3. Record one **provider outcome triage**, using the decision enforced for that precise provider status. Supply a dated non-personal source reference to real provider evidence or an internal exception note.
4. **Only after triage**, independently record one recipient confirmation if the real recipient explicitly acknowledged the gift through a direct reply or a verified phone conversation; a provider receipt must never be used in place of their acknowledgment.
5. If there is missing, contradictory or delayed evidence, record one **no-resend escalation** with a clear reason and offline source reference. No automatic outreach is initiated.

The three review kinds are independent append-only records, with at most one of each per one-time attempt. Records capture immutable provider-status snapshots, evidence source and reference, timestamp, SHA-256 fingerprint and owner ID. A separate operator made the prior Build 687 dispatch; the owner cannot spoof that role. Invalid date, case/gift mismatch, repeated event, status drift or missing review prerequisites fail closed in the database transaction.

## Safety boundary

Build 688 has **no email/SMS provider bridge, no payment provider call, no queueing and no gift mutations**. The administrative UI calls `/api/admin/gift_delivery_outcome_review` for GET/POST. The POST handler invokes only the `record_gift_delivery_outcome_review` Supabase RPC; a transaction-scoped lock protects the exact checkout session. Owner identity must come from a signed session, never a legacy password fallback. The database enforces least privilege (RLS, service role only) and append-only evidence. The admin page explicitly requires three confirmations before saving.
