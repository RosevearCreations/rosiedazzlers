# Rosie Dazzlers Build 720 — Provider Drift, Reviewer Recovery & Protected Owner Ledger Gate

## Release scope

Build 720 adds three compact management-only workflows inside the existing Staff Follow-Up Workload page. All new operations require a genuine signed-in administrator session, use bounded original source evidence, and are fail-closed. The distinction is crucial: **software deployment can be GREEN while live external approvals and independently supplied evidence remain HELD.** No test fixture constitutes a real provider, custodian, witness or owner.

### 1. Provider binding freshness and source-drift alerts

1. Select the staff member and future planned hour.
2. **Download signed baseline** requests an actual configured HTTPS shift-provider GET, checks staff eligibility, absences, shift coverage, pinned provider origin and account, then signs the bounded provider-binding readback with the configured server Ed25519 key. This requires a live bound source; absence-only records do not count as shift hours.
3. Keep the *original* downloaded signed envelope. On a later check for the **same staff member and exact hour**, upload it and select **Compare live source to signed baseline**.
4. The server checks the original signature against the **current** configured signing key and then performs a fresh GET. It returns a downloaded manual alert: `NO_DRIFT_OBSERVED`, `ROSTER_CONTENT_OR_REVISION_CHANGED_REVIEW`, `PROVIDER_OR_ACCOUNT_PIN_DRIFT`, `CURRENT_PROVIDER_SOURCE_STALE`, or another explicit HOLD. Alerts do **not** send messages or automatically reassign work.

Signed baselines older than 30 days, changed signer keys, invalid signatures, mismatched staff/window and stale live sources are refused or marked HOLD. The signed baseline and comparison result stay with the operator as local downloads; no fabricated long-term history is implied. A change of roster response hash can reflect source metadata as well as shift rows, so a `review` alert requires human examination.

### 2. Independent custody reviewer receipt recovery

The designated currently authenticated reviewer must upload an **original server-signed Build 719 custody disposition**, not a manually edited summary. The backend verifies the signature, current signer identity, exact reviewer account, witness payload fingerprint and internal-only scope. It returns a read-only local recovery document. It does **not** claim the reviewer is a verified independent human, that a durable server receipt exists, or that external Proof-B evidence has been obtained. Replaced/rotated keys require a separate documented key-migration process; old signatures do not silently pass.

Configuration retained from earlier builds:

- `ROSIE_FOLLOWUP_EXPORT_ED25519_PRIVATE_JWK` — genuine securely stored server signing **secret**, never committed or exposed to clients.
- `ROSIE_FOLLOWUP_EXPORT_SIGNER_ID` — corresponding server signer identifier.
- `ROSIE_FOLLOWUP_EXPORT_SIGNER_STAFF_ID` — originating staff UUID.
- `ROSIE_EXPORT_CUSTODY_REVIEWER_STAFF_ID` — distinct authorized reviewer UUID.
- `ROSIE_EXPORT_CUSTODY_WITNESS_PUBLIC_JWK` and `ROSIE_EXPORT_CUSTODY_WITNESS_ID` — independent witness public key and id, required for **new** Build 718/719 witness verification, not generated by recovery.

### 3. Protected owner-evidence ledger approval gate

The owner first obtains a genuine Build 719 signed `PROTECTED_HASH_LEDGER_REQUEST_HELD` evidence-retention request. A **different**, currently signed-in administrator with UUID matching the new `ROSIE_OWNER_EVIDENCE_LEDGER_REVIEWER_STAFF_ID` can upload that exact file, propose a hashes-only retention period (7, 30 or 90 days), enter a non-private review note, explicitly acknowledge that no ledger is active, and download a separately server-signed scope-limited review receipt.

- Decisions: `LEDGER_APPROVAL_GATE_HELD` (request schema/security review) or `LEDGER_REQUEST_REJECTED`.
- No table, RLS policy, migration, append-only store, approval write, background retention, device certification or owner-proof persistence has been authorized or created.
- A future retention feature **must separately receive** a schema/privacy design, least-privilege policies, explicit owner authorization and independent review **before any data write**. No sensitive raw owner-device files should be stored by this gate.

The private binding must be configured through Cloudflare's protected environment, with the actual distinct reviewer UUID, before the gate can produce a signed result. Never use a synthetic test UUID for real approval.
