# Rosie Dazzlers Build 766 — Independent Owner Closure Authorization, Append-Only Decision Receipt & Final Exception Disposition Gate

**A read-only, signed-evidence handoff — not an executable closure workflow.** No website-initiated SQL, database connection, ledger mutation, authorization replay grant, rollback, customer communication or business closure. Build 765’s independent DBA/audit evidence is re-fetched and reauthenticated from fixed server-owned sources for each request; a browser-supplied unsigned Build 765 packet is never authorization.

## Strict independent chain

1. **Original owner explicitly authorizes an external manual review or signs HOLD.** The owner imports a new domain-separated Ed25519 envelope using the original `ROSIE_ECONOMIC_OWNER_RECEIPT_*` public key ID. The signing domain is `rosie-owner-independent-closure-authorization-v766:` and the canonical field order is `OWNER_AUTH_FIELDS766`. Required exact scope includes booking/source UUIDs, change ticket, execution request, production project, Build 764 owner post-change receipt, Build 765 independent DBA/audit inspection receipt digests, Build 765 owner readiness receipt, independent new authorization ticket, nonce and issuance time. Only `AUTHORIZE_EXTERNAL_MANUAL_CLOSURE_REVIEW_ONLY` or `HOLD_FINAL_CLOSURE_EXCEPTION` is allowed. A valid HOLD is always honored even after a clean Build 765 review. A signature never becomes permission for this website to mutate business state.
2. **Signer 22: independently signed append-only decision custodian.** Server-owned bare HTTPS `ROSIE_ECONOMIC_CLOSURE_DECISION_CUSTODIAN_BASE_URL` (GET `/v1/economic-closure-ledger-decision-v766`) provides an envelope signed with the unique `ROSIE_ECONOMIC_CLOSURE_DECISION_CUSTODIAN_PUBLIC_KEY_B64` / `..._KEY_ID`. Domain: `rosie-external-append-only-closure-decision-v766:`. The canonical `LEDGER_FIELDS766` bind the exact owner decision digest, original owner readiness, Build 765 immutable audit receipt and independent log-chain/retention hashes. Custodian provides an external ledger entry ID, previous and new entry digests, storage-enforcement proof digest, literal stored owner decision, and outcome `APPEND_ONLY_DECISION_RECORDED_EXTERNAL` or `STORAGE_EXCEPTION_HOLD`. Original object-store retention controls, custody, previous-chain validation, and source write-once enforcement remain outside the app. Even a correct signature authenticates a **claim** about recorded storage, not proof of permanent immutability.
3. **Signer 23: independent final exception reviewer.** Server-owned bare HTTPS `ROSIE_ECONOMIC_FINAL_EXCEPTION_DISPOSITION_REVIEWER_BASE_URL` (GET `/v1/economic-final-exception-disposition-v766`) returns a separate Ed25519 envelope using `ROSIE_ECONOMIC_FINAL_EXCEPTION_DISPOSITION_REVIEWER_PUBLIC_KEY_B64` / `..._KEY_ID`; domain `rosie-independent-final-exception-disposition-v766:`. Canonical `DISPOSITION_FIELDS766` bind exact ticket/project, owner authorization, custody receipt, DBA/audit receipt digests, independent incident and exception register digests, unresolved critical count, state and reviewer timestamp. Positive handoff requires explicit owner external-review authorization, a clean custodian signed receipt, **zero** unresolved critical exceptions, `NO_OPEN_EXCEPTION_CLAIM`, and `AUTHORIZED_FOR_SEPARATE_MANUAL_CLOSURE_HANDOFF`. Any other claim must be `FINAL_EXCEPTION_HOLD` with `EXCEPTIONS_OPEN_HOLD`. A signed HOLD cannot be overwritten by the browser.

All **23** signer public keys and key IDs must be distinct, including the 21 historical keys, and all **14** provider origins must be distinct, pinned server-side HTTPS bare origins. Only two-field envelopes (`payload`,`signature_b64`) using canonical ordered strings and Ed25519 verification are accepted. All new timestamps follow the preceding signed observations and are no older than seven days. Public verification keys and origin URLs are configured server-side. Never store private keys in Cloudflare or browser assets. DNS re-binding defenses, network egress policy, signer independence, one-time nonce enforcement, actual external ledger state and independent witness custody require an external security audit; this build does not provide them.

## Decision boundaries

- Full clean historical chain, owner explicit authorization, clean append-only custody attestation and independent final no-exception claim: `READY_FOR_SEPARATE_CONTROLLED_EXTERNAL_CLOSURE_HANDOFF`.
- Missing provider/configuration, invalid/duplicated key, malformed signature, project/ticket mismatch, stale or future timestamp, owner HOLD, storage incident, nonzero critical exception count, or conflicting signed source: `HOLD_FINAL_OWNER_AUTHORIZATION_CUSTODY_OR_DISPOSITION` with follow-ups.
- In **every** result, `external_closure_executed_or_verified_by_app`, `immutable_ledger_verified_by_app`, `production_db_connected_by_app`, `owner_closure_audit_persisted_by_app`, `customer_notifications_sent_by_app`, `closure_allowed` and `automatic_business_write` remain false.

The final handoff is **not** an assertion that a booking/economic exception has actually been closed. An externally approved change manager and operator must separately execute, log and independently verify any closure, and obtain a new business record outcome receipt. No genuine external signer/provider or owner receipts are shipped with this code; operational closure remains **HOLD**.

## Owner use

1. Confirm the actual independent Build 765 DBA/immutable audit work has happened; preserve the source reports and custody outside the website.
2. Have the owner sign a new Build 766 explicit manual-review authorization or HOLD with the original signing identity, exact ticket and new authorization ticket.
3. Have an independent custodian append and sign the decision in their controlled external ledger, including a verified previous-entry chain, then a *different* final exception reviewer sign the true incident/exception status.
4. In Admin → Build 766, enter the four exact identifiers and import the three authentic owner signed JSON decisions (Builds 764, 765 and 766). The application reads fixed independent custody/disposition sources; download an **unsigned** packet for handoff.
5. On a positive handoff, separately authorize and record any actual closure. This screen cannot close, modify or notify anyone.
