## Scope and truth boundaries
Build 879 provides an authenticated original-owner monitoring **snapshot**, source-bound owner acknowledgment renewal guidance, and supervised verification of an already operator-executed pinned Ed25519 issuer configuration change. It cannot manufacture longitudinal history, activate a provider webhook, acknowledge an owner's SLA, edit Cloudflare environment bindings, sign with a private issuer key, assert a third-party witness, send messages or clear financial HOLD.

### 1 — Original delivery watch
Signed-in original Admin GET `/api/admin/roadside_stability_watch_v879?draft_id=<UUID>` re-evaluates Build 878's original signed native Resend webhook/live account correlation and private dispatch evidence along with Build 878's owner SLA custody. The reply excludes names, addresses, original tokens, signing secrets and source JSON; it returns original native chain digest, timestamp and provenance status. A currently corroborated source is only `ORIGINAL_DELIVERY_CURRENT_SNAPSHOT`; signed events older than 30 days yield `ORIGINAL_DELIVERY_AGED_REVIEW`. Mismatched/missing origins remain `HOLD`. In the browser, repeated manual checks compare the prior in-memory digest and flag changed chains for manual review; this is **not** a persistent historical monitor, background watch or independent uptime attestation.

### 2 — Current original SLA acknowledgment renewal
The same owner request reads the private source-bound Build 878 acknowledgment status, classifying `OWNER_SLA_RENEWAL_REQUIRED` only for an original open case with an unacknowledged new original source-check ID or changed severity. The existing authenticated Build 878 POST performs the immutable actual owner acknowledgment, requiring same-origin owner action, revalidated live sources, original open case and 12–500 character note; no prior rows are changed. Original immutable case `opened_at` and SLA deadlines never reset. An unknown or truncated source remains `OWNER_SLA_RENEWAL_HOLD`.

### 3 — Supervised issuer rotation execution and verification
**Manual operator prerequisite:** a responsible authorized operator must actually update `ROSIE_CLOSURE_TRUSTED_ED25519_KEYS_JSON` securely in the **Cloudflare Pages environment**, after independently enrolling the successor signing key. The target roster contains exactly one distinct new `active` key and the verified old key as `previous` with an explicit `issued_before` and future `verify_until` grace period. Avoid placing private signing material in this roster, code, PRs, browser inputs or GitHub issues. Confirm authorized deployment of the new Cloudflare configuration separately.

On the signed-in Admin Bookings screen, choose the original draft and the same original Build 874 signed closure dossier and Build 877 Ed25519 sidecar used in Build 878. Enter both trusted **public key fingerprints**, a substantive owner note and press **Verify supervised post-rotation operator pins**. Owner POST `/api/admin/roadside_rotation_execution_v879` requires exact same-origin request, an explicit owner statement, an Admin session, and a fresh successful original private-source/digest and independently pinned previous-key signature verification before checking the new active operator pin. It returns `POST_ROTATION_OPERATOR_PIN_CONFIRMED` only while the old signed proof remains verifiable in the configured grace window and new active fingerprint is distinct. It makes **no** Cloudflare edit or permanent owner ceremony record. This is a snapshot of **deployed server configuration**, not proof of an independently witnessed physical change or a complete rotation of signing authority. Without actual original keys and operator action this is **ROTATION_HOLD**. Retain previous public pins until historical validation policy allows expiry; revoked pin always HOLD.
