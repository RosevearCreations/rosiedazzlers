# Rosie Dazzlers Build 768 — Independent Owner Post-Closure Acceptance, Original-Source Custody Reconciliation & Exception Reopening Controls

**Read-only evidence review and owner handoff.** No website execution of SQL, production database changes, ledger append, business closure, customer notification, owner-acceptance recording, or exception reopening. No authentic external provider, owner signatures or source receipts are bundled. Software GREEN never means a real booking/economic case was closed.

## Strict original evidence chain

1. Re-fetch and independently verify the *entire* Build 764–767 chain on every authenticated same-origin owner review: original signed owner post-change decision (764), readiness decision (765), external-manual-review authorization or HOLD (766), independent external operator witness (767), and independently signed post-closure state inspection (767). Signed owner decisions are imported as original JSON envelopes. Browser-generated summaries are not source authority.
2. The **original owner key** signs one Build 768 decision using `canonicalOwner768` (`OWNER_FIELDS768`) and domain `rosie-owner-postclosure-acceptance-decision-v768:`. The payload binds booking/source UUIDs, original trial/project/change/request, prior externally signed operator/inspector hashes, original DBA/audit receipt hashes, a fresh owner decision ticket, owner ID, time and nonce. Only `ACCEPT_FOR_SEPARATE_MANUAL_OWNER_REVIEW_ONLY`, `REOPEN_EXCEPTION_FOR_EXTERNAL_REVIEW` or `HOLD_OWNER_POSTCLOSURE_ACCEPTANCE` is permitted. This is evidence for a separately controlled manual action, never executable authorization to this website.
3. **Signer 26 — original-source custodian.** Server-owned bare HTTPS `ROSIE_ECONOMIC_ORIGINAL_SOURCE_CUSTODY_RECONCILER_BASE_URL` serves `GET /v1/economic-original-source-custody-v768`, signed using a *distinct* `ROSIE_ECONOMIC_ORIGINAL_SOURCE_CUSTODY_RECONCILER_PUBLIC_KEY_B64` and `..._KEY_ID`. Domain `rosie-original-source-custody-reconciliation-v768:` and fixed `CUSTODY_FIELDS768` bind the owner decision, original operator result, independent inspector and Build 765 DBA/audit receipt digests, previous/new custody hashes and retention policy. Only `ORIGINAL_SOURCES_INDEPENDENTLY_RECONCILED_CLAIM` or `ORIGINAL_SOURCE_CONFLICT_HOLD` is recognized. The signing party's original storage controls, object retention and immutable history must still be independently audited externally.
4. **Signer 27 — exception/reopening reviewer.** A separately pinned bare HTTPS `ROSIE_ECONOMIC_EXCEPTION_REOPEN_REVIEWER_BASE_URL` serves `GET /v1/economic-exception-reopen-review-v768` signed with a different `ROSIE_ECONOMIC_EXCEPTION_REOPEN_REVIEWER_PUBLIC_KEY_B64` and `..._KEY_ID`. The `REOPEN_FIELDS768` domain is `rosie-independent-exception-reopening-v768:` and binds exact scope, owner/custody receipt hashes, incident and exception register digests, case ID, unresolved critical count, result and independent time. `NO_NEW_EXCEPTION_CLAIM` requires the owner's manual review decision, clean original custody and **zero** critical exceptions. `EXTERNAL_REOPEN_REQUEST_RECORDED_CLAIM` requires an original-owner signed reopen request and remains HOLD pending real-world verification. `EXCEPTION_REVIEW_HOLD` never clears an exception. This is independent signed *claim* verification, not a website case write.

All **27** public Ed25519 signing identities/IDs must be unique across historical and new roles; all **18** original provider origins must be distinct server-owned bare HTTPS origins. Exact canonical strings and signing domain prevent cross-role replay. Evidence is chronologically ordered, no older than seven days and at most five minutes in the future. Unexpected fields, duplicate keys, origin duplication, provider errors, stale/noncanonical signatures, conflicting hashes or nonzero exceptions fail closed. Never configure private signing keys in Cloudflare or the browser. DNS re-binding controls, external nonce replay prevention, original source authenticity beyond the signer claim and storage write-once enforcement require independently controlled systems.

## Review outcomes

- Complete clean external chain, original owner manual-review decision, clean custody claim, independent zero-critical-exception claim: `READY_FOR_SEPARATE_MANUAL_OWNER_ACCEPTANCE_HANDOFF` **only**. A new manual original-owner business acceptance outside the website remains required.
- Owner HOLD, explicit signed exception reopening, custody conflict, stale/missing independent receipt, unresolved critical exception or any mismatch: `HOLD_ORIGINAL_CUSTODY_OWNER_DECISION_OR_REOPEN_EXCEPTION`, with exact follow-ups. A signed external reopening claim is never silently converted to success.
- `owner_acceptance_recorded_by_app`, `external_case_reopened_by_app`, `actual_business_closure_verified_by_app`, `production_db_connected_by_app`, `immutable_storage_verified_by_app`, `automatic_business_write`, `closure_allowed` and `customer_notifications_sent_by_app` remain false in every outcome.

## Owner steps

1. Verify the original Build 767 operator and inspector reports independently. Preserve the actual source files, signed envelopes, audit evidence and change-manager authority outside the application.
2. Sign a new Build 768 manual-review decision, external exception reopening request or HOLD using the original owner identity, exact scope and fresh nonce/ticket.
3. Have an outside original-source custodian reconcile the retained operator/inspector/DBA/audit files and sign the source-custody result. Have a *different* reviewer attest the real exception register and any actual reopening request.
4. In Admin → Build 768, enter the four identifiers and import all four authentic owner-signed JSON envelopes. Source custody and exception review are fetched only from server-pinned independent sources. Download the **unsigned** packet for the owner handoff.
5. Handle any HOLD manually and confirm any actual external case reopening/acceptance against original records. Do not interpret website GREEN as a real business action.
