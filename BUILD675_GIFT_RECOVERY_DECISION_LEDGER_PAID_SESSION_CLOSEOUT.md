# Build 675 — Gift Issuance Recovery Decision Ledger, Paid-Session Cross-Check & Customer-Safe Exception Closeout

## Owner workflow

1. Find the Stripe Checkout session ID in the authorized payment record; open Admin → Site Settings → Build 674 issuance review to inspect atomic receipt, webhook replay/hold events and certificate count.
2. In Build 675, **Cross-check Stripe and decision ledger**. Only an authenticated owner can see the read-only check. The server reads the Checkout session **and its line items** from Stripe, checks settled payment (`paid`), completed payment-mode session, `purpose=gift`, matching cart/line quantities (maximum 100), payment intent, positive paid total, currency and test/live correspondence. No purchaser name, email, cart, gift code, payment intent or raw provider response is returned to the browser.
3. Select **Keep recovery hold**, **Escalate for independent review**, or **Close verified issuance (no customer action)** with a preset non-PII reason. A closeout requires the specific “verified, no duplicate action” reason and explicit acknowledgment. Each save rechecks Stripe on the server; an RPC then takes the Build 674 advisory session lock and verifies the *current* receipt and certificate counts, continuous 1–N checkout lines, payment intent and currency, no held webhook events, issued event evidence, and no unresolved delivery statuses. Only then is a closeout entry appended. The RPC does not release a historic hold.
4. Confirm the new entry in the ledger after saving. A missing receipt, held replay, unpaid or unavailable Stripe session, mismatched certificate count, legacy missing checkout line, or unresolved `failed` / `review_required` / `processing` delivery **cannot be marked verified**. Maintain/escalate entries can be recorded with an unavailable provider, explicitly retaining the hold.

## Non-negotiable safety

- The table is RLS-enabled and service-role-only. Grants permit SELECT and INSERT, not UPDATE/DELETE. The narrowly validated SECURITY INVOKER RPC is service-role-only; the application performs signed-in owner checks and does not accept legacy x-staff-email/id bridge identity for financial evidence.
- The decision ledger stores provider status/amount/count, SHA-256 safe evidence fingerprint, actor ID, reason enum and atomic database counts only. No customer email, gift code, API key, card data, webhook payload or free-text notes.
- Neither GET nor POST creates payment, certificate, replacement, refund, notification, balance change or delivery retry. A verified *issuance* closeout is **not** proof of customer email delivery; scheduled delivery and separately held notifications still need independent review.
- Database RPC checks are transactional under the same per-session lock as Build 674 issuance. HTTP uncertainty should be reconciled by decision UUID before submitting again; duplicate UUID with conflicting evidence is rejected.
- The migration is additive and must be applied to the intended Supabase environment before enabling POST. No real paid session, customer charge, refund or email is generated by Build 675 tests.

## Acceptance

- `bash scripts/current_gift_issuance_regression.sh` verifies Builds 673–675: paid/unpaid provider checks, line counts, provider outage, origin/owner access, holds, no outbound payment/email operations and safe ledger contracts.
- Database migration must pass SQL compile, RLS/grant checks and an always-rolled-back synthetic decision/counterexample transaction. Source checks and exact SHA Cloudflare Development/Production acceptance remain separate release gates.
- On the connected Rosie Dazzlers Supabase project, the Build 675 decision-table migration and append-only guard were applied. Database privilege probes confirmed service-role SELECT/INSERT allowed but UPDATE/DELETE denied, anon SELECT denied, RLS enabled and one active reject-UPDATE/DELETE trigger. The separately applied rollback-canary migration executed a successful paid/consistent issuance closeout, confirmed repeated-decision idempotency, rejected closeout after a held webhook, and deliberately rolled back all synthetic records in a nested exception block. Subsequent independent SQL read confirmed **0 certificates, 0 receipts, 0 events and 0 decisions** remain for the canary session. This checks Postgres behavior, not a live Stripe transaction.
- Read-only production Stripe GET is executed only when a real authenticated owner enters an existing session ID; CI uses mocked Stripe responses and never attempts a live charge.
